# Build & Deploy

## Hosting

The portfolio is served by **GitHub Pages**, configured to publish from
the `master` branch's `/docs` directory via the GitHub Actions
deployment workflow (`actions/deploy-pages@v5`). The deploy is
**not** a "branch-based" Pages deployment — there is no `gh-pages`
branch.

Custom domain: `www.sauravbhattacharya.com` (DNS managed outside this
repo). The `CNAME` file lives inside `docs/` so it ships with every
deploy.

## Deployment trigger

`.github/workflows/pages.yml` runs on:

1. Pushes to `master` that touch `docs/**` or the workflow file
   itself.
2. Manual `workflow_dispatch`.

Pushes that only touch tests, CI config, or top-level Markdown **do
not** redeploy the site — that's intentional, to keep the deploy
queue short.

## SRI verification

The first step of the deploy job is an SRI sanity check:

```bash
cd docs
for file in app.js style.css; do
  expected=$(grep -oP "(?<=$file\" integrity=\")[^\"]*" index.html)
  actual="sha384-$(openssl dgst -sha384 -binary "$file" | base64 -w0)"
  test "$expected" = "$actual"
done
```

If the hash in `index.html` doesn't match the on-disk bytes, the
deploy fails fast with a copy-pasteable fix command. The same check
runs in `tests/score-and-search.test.js` indirectly (the load helper
parses the page) so most drift is caught locally before push.

## Deployment steps (verbatim from the workflow)

1. `actions/checkout@v6`
2. SRI verification (see above)
3. `actions/configure-pages@v6`
4. `actions/upload-pages-artifact@v5` (path: `docs`)
5. `actions/deploy-pages@v5`

The job runs in the `github-pages` environment, which gates which
branches can deploy. **Don't change the environment name** without
also updating the repository settings.

## Rollback

There is no automatic rollback. To revert a bad deploy:

```bash
git revert <bad-commit>
git push origin master
```

GitHub Pages will redeploy from the new tip within ~1 minute.

## Sitemap & robots.txt

- `docs/sitemap.xml` is regenerated by `scripts/refresh-sitemap.js`.
- `docs/robots.txt` is hand-maintained — disallow rules are added
  there, never to individual pages.

Both files are part of the static asset bundle uploaded to Pages.

## Lighthouse CI

`.github/workflows/lighthouse.yml` runs Lighthouse against the
deployed site once a day and on every push to `master`. The job is
**informational** — it reports scores but does not fail builds. Use
the report to spot regressions; act on them as bug-fix tasks.

## Local "build"

There is no local build step. The bytes in `docs/` are the bytes
deployed to Pages, modulo Pages' own gzip / `Cache-Control` handling.
That's the whole point of [the no-bundler architecture](architecture.md#-design-rationale-no-bundler).
